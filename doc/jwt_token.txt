La SECRET_KEY est la clé de signature cryptographique qui permet au serveur de prouver qu'un token (JWT) a bien été émis par lui, et qu'il n'a pas été modifié par un tiers. C'est le sceau de ton application.

Ce qui se passe concrètement
1. À la connexion — le serveur signe le token
Quand un utilisateur se connecte, ton code fait :

python
payload = {"sub": "42", "email": "bob@mail.com", "exp": ...}
token = jwt.encode(payload, SECRET_KEY, algorithm="HS256")
Le JWT est composé de 3 parties séparées par des points :

text
eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiI0MiIsImVtYWlsIjoiYm9iQG1haWwuY29tIn0 . 3Kp9xQ7vB...
     ↑ header (algo)              ↑ payload (données)              ↑ signature
La 3ᵉ partie (signature) est calculée par HMAC-SHA256 :

text
signature = HMAC_SHA256(header + "." + payload, SECRET_KEY)
Autrement dit : la signature dépend de la clé secrète. Seul ton serveur peut la produire.

2. À chaque requête — le serveur vérifie la signature
Quand le client renvoie le token, ton middleware fait :

python
jwt.decode(token, SECRET_KEY, algorithms=["HS256"])
Le serveur recalcule la signature avec la même SECRET_KEY et la compare à celle du token. Trois cas :

Cas	Résultat
Signature valide	                    Le token a bien été émis par ton serveur → utilisateur authentifié
Signature différente	                Token forgé ou modifié → 401
Signature faite avec une autre clé	    Même chose → 401
Sans la clé secrète (ou si elle est faible/fuit)
Un attaquant peut fabriquer n'importe quel token de son côté :

python
# L'attaquant, avec ta SECRET_KEY
faux_token = jwt.encode({"sub": "1", "email": "admin@site.com"}, SECRET_KEY, "HS256")
Puis l'envoyer à ton API → ton serveur recalcule la signature, elle correspond (même clé), donc il accepte. → L'attaquant est admin sans mot de passe. C'est pour ça que la clé doit rester secrète et être longue et aléatoire.

Analogie simple
Imagine un cachet de notaire :
Le notaire (ton serveur) appose son cachet (la signature) sur un document (le token).
N'importe qui peut lire le document (le payload JWT est juste du base64 — pas chiffré).
Mais personne ne peut imiter le cachet sans le tampon (la SECRET_KEY).
Quand quelqu'un présente un document, le notaire vérifie le cachet → si c'est le sien, il fait confiance.

Conséquence importante : le payload JWT n'est pas chiffré, juste signé. Donc ne mets jamais de données sensibles dedans (mot de passe, numéro de carte, etc.). Un JWT ne cache rien, il prouve juste.

Récap de ce que fait la SECRET_KEY
Rôle	Détail
Signer les JWT à la création	jwt.encode(..., SECRET_KEY, ...)
Vérifier les JWT à chaque requête	jwt.decode(token, SECRET_KEY, ...)
Garantir l'intégrité du token	Si un octet change, la signature ne correspond plus
Garantir l'authenticité	Seul ton serveur peut produire des tokens valides
Invalider toutes les sessions si on la change	Utile en cas de fuite

Bonnes pratiques liées
Longue et aléatoire : 32+ octets (la commande secrets.token_urlsafe(64) te donne ça).

Une clé par environnement : différente en dev / staging / prod. Ne jamais réutiliser celle de prod en dev.

Jamais dans Git, jamais dans les logs, jamais dans une réponse HTTP.

Rotation possible : si tu changes la clé, tous les tokens existants deviennent invalides → tous les utilisateurs doivent se reconnecter. C'est normal et voulu (utile en cas de fuite).

Différente de la clé de chiffrement des mots de passe : les mdp sont hashés avec bcrypt (irréversible), ce n'est pas la même chose. La SECRET_KEY ne sert pas à hacher les mots de passe.

Ce qu'elle ne fait PAS
 Elle ne chiffre pas les données du token (le payload est lisible par tous).
 Elle ne stocke pas les sessions (les JWT sont stateless : le serveur ne garde rien en mémoire, tout est dans le token).
 Elle ne remplace pas le hachage des mots de passe (bcrypt/passlib gère ça).
 Elle ne protège pas contre le vol de cookie (pour ça : HttpOnly, Secure, SameSite, HTTPS).

En résumé : SECRET_KEY = la clé qui permet à ton serveur de signer et vérifier les tokens. C'est elle qui transforme un bout de JSON public en preuve d'identité inviolable. Si elle fuit, ton auth est cassée. Si elle est solide et secrète, tout le système tient debout.
